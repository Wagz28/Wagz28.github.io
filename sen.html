Sen

A personal assistant built as a system: one core, many deletable clients, and a fast control loop that always beats the slow one.

Overview

Sen (short for Seneschal) is my voice and chat assistant. I can talk to it from my PC, my phone or a website, and it can set reminders, take notes, track work items and start AI coding sessions on my home server to do longer jobs. The interesting part is not any one feature but how it is built: every piece is replaceable, and nothing depends on a model behaving.

How it is built

  • Contracts first. Every boundary is a written schema with a conformance test. Implementations can be swapped as long as they pass.
  • Core and clients. The core is the data plus the API over it. The site, the Android app, voice and AI sessions are all clients. Deleting any client loses no data, and the test suite checks that.
  • Security at the contract. Each client has its own identity and scopes, data carries sensitivity tags, and every release of sensitive data is logged.
  • Fast and slow paths. A deterministic loop owns control (stop, pause, modes). The LLM loop never speaks directly; its output passes through the fast path's gate.
  • Thin vertical slices. Each contract is proven end to end with one small feature before anything widens.

Everything runs on my own machines, joined by a private encrypted network. Encryption and identity live at that bottom layer, so nothing above has to reimplement them. There are three routes through the system.

Talking to Sen

The phone app's voice tab, or my PC's microphone, is just a pipe: it streams audio and holds no logic. The fast path does the listening, and the brain's reply only comes back out through the gate.

Typing to Sen

Typed chat never goes straight to the model. It is written into core, the brain picks up what is unread, and its reply is written back. Close the app mid-reply and nothing is lost.

Fast and slow

Borrowed from Thinking, Fast and Slow. Sen's brain is a small model running on my own server; when it can't handle a request it hands it up to Claude. The fast path needs no LLM and answers in milliseconds; the slow path thinks, plans and calls tools. Saying "stop" always works, however busy the slow path is.

Callosum

Named after the bridge between the brain's hemispheres, Callosum links my machines and the AI coding sessions running on them. It keeps one shared environment across computers, reports each machine's status, lints the setup nightly, and runs a weekly scan that proposes, but never makes, changes. Sen uses it to start, watch and hand work to sessions, so a request spoken to my phone can end as a reviewed change in a repository.

Stack

  • Python standard-library HTTP servers, SQLite, pytest
  • Kotlin + Jetpack Compose (native Android, no WebView)
  • Wyoming protocol for speech, ntfy for messaging, MCP for tools
  • Local LLM (Qwen3-4B via llama.cpp) as Sen's brain, escalating to Claude when it can't answer
  • Claude Code (headless) for escalation and sessions
  • Tailscale, systemd, tmux, Syncthing

Vision

The aim is an assistant I own end to end: my data in one core I control, any interface I like on top, and AI as a client rather than the foundation. Pull every model out and the system still works by hand. Put a better one in and nothing else has to change. Over time I want Sen to take on more of the routine running of my life and work, while control stays with the fast, predictable layer and with me.
